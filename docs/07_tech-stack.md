# 07. 技術スタック選定

> 選定基準は一貫して「**家族数人で使うアプリを、個人が無料〜最小コストで作り切り、放置気味でも運用が破綻しないこと**」。
> 汎用的な優劣ではなく、この前提での判断であることに注意。

## 1. 採用スタック一覧

| 領域 | 採用 | バージョン |
|------|------|-----------|
| フレームワーク | Next.js（App Router） | 16.2.x |
| UI | React | 19.2.x |
| スタイリング | Tailwind CSS | 4.x |
| 言語 | TypeScript | 5.x |
| BaaS | Supabase（Auth / Postgres / Storage） | クラウド無料枠・東京 |
| Supabase 連携 | @supabase/supabase-js + @supabase/ssr | 2.x / 0.12.x |
| ホスティング | Vercel | Hobby |
| リポジトリ / CI | GitHub（main push → Vercel 自動デプロイ） | ― |
| Lint | ESLint（eslint-config-next） | 9.x |

## 2. 主要な選定理由

### Next.js + Vercel

- スマホ「Web」アプリ（PWA）が要件（FR-X-1）。ネイティブアプリはストア審査・開発コストが過剰
- App Router の RSC で「初期表示は SSR・操作はクライアント」を素直に書ける。
  参照速度（NFR-P-*）が製品価値の中心なので、初期表示に JS 実行を待たない構成は要件に直結する
- GitHub 連携で push だけの自動デプロイ。個人運用での継続性を優先

### Supabase

- 認証（Google OAuth）・RLS 付き Postgres・ファイルストレージが 1 サービスで揃い、無料枠で足りる
- **RLS を認可の本体にできる**ことが決め手。自前 API を書かない構成
  （[06_api-design.md](06_api-design.md) §4）は Firebase のセキュリティルールでも可能だが、
  リレーショナルなデータ（家族→子供→靴）と SQL での検証しやすさで Postgres を選好
- CLI（マイグレーション / config push）で構成をコード管理できる

### Tailwind CSS 4

- 画面数が少なく（6画面）、コンポーネントライブラリを入れるほどではない
- モバイル特化のシンプルな UI をユーティリティだけで素早く組む

## 3. 選定の経緯・変更履歴

| 時期 | 決定 | 経緯 |
|------|------|------|
| 計画時 | ローカル開発は Supabase CLI + Docker（OrbStack） | 標準的な開発フロー想定 |
| M0 実施時 | **ローカル Supabase を廃止し、クラウド無料枠へ全面移行** | 開発機のディスク（残数GB）とメモリの制約で Docker スタックが安定稼働しなかった。ローカル/クラウドの環境差異リスクより開発が止まるリスクを重く見た |
| M0 実施時 | 開発用パスワード認証を追加（env で出し分け） | Google OAuth 設定前に開発を進めるため。本番では無効化済み |
| デプロイ時 | git 連携の自動デプロイを採用 | 手動 `vercel deploy` の打ち忘れ・打ち間違い防止 |

## 4. 意図的に採用しなかったもの

| 不採用 | 理由 |
|--------|------|
| 状態管理ライブラリ（Redux 等） | サーバー状態は RSC + `router.refresh()`、ローカル状態は useState で足りる規模 |
| フォームライブラリ / バリデーションライブラリ | フォームは実質2つ。DB 制約 + ネイティブ input で十分 |
| ORM（Prisma / Drizzle） | クエリは supabase-js で完結。マイグレーションは SQL 直書きの方が RLS・トリガーと相性が良い |
| テストフレームワーク一式 | セキュリティ境界（RLS）のみ専用スクリプトで統合テスト。UI の自動テストは費用対効果が合わない規模 |
| アクセス解析 | プライバシーポリシー整備の負担を避ける（[09_legal-operational-concerns.md](09_legal-operational-concerns.md)） |
| モノレポ / Turborepo | 単一アプリに不要 |

## 5. バージョン管理・更新方針

- Next.js 16 は本書執筆時点の最新系。**破壊的変更が多いため、コード作成前に
  `node_modules/next/dist/docs/` 配下の同梱ドキュメントを参照すること**（AGENTS.md の規約）
- 依存更新は「動いているものを壊さない」を優先し、セキュリティ修正以外は急がない
