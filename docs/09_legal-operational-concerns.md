# 09. 法的・運用上の懸念事項

> 前提: 利用者は自分の家族のみ（不特定多数への公開はしない）。
> この前提が変わる場合、本書の大半の判断は見直しが必要になる。

## 1. 法的・プライバシー面

### 1.1 扱う個人情報

| データ | 内容 | 感度 |
|--------|------|------|
| アカウント | メールアドレス、Google アカウントの表示名 | 中 |
| 子供の情報 | 名前（呼び名）、靴のサイズ | **高（子供に関する情報）** |
| 写真 | 靴・保管場所の写真 | 中（生活空間が写り得る） |

### 1.2 判断と対応

| 論点 | 判断 | 根拠・条件 |
|------|------|-----------|
| プライバシーポリシー / 利用規約 | **MVP では作成しない** | 利用者が運営者自身の家族のみで、第三者への「提供」に当たる利用がない。アクセス解析も広告も入れない（この負担回避が解析ツール不採用の理由。[01_requirements.md](01_requirements.md) §2.2） |
| 子供の名前 | フルネームではなく呼び名（「長男」等）を推奨 | UI のプレースホルダで誘導。強制はしない |
| 写真の非公開性 | Storage バケットは非公開 + RLS + 期限付き署名 URL のみ | 公開 URL は存在しない |
| データ越境 | Supabase 東京リージョン / Vercel（CDN はグローバル） | 家族利用の範囲で問題なし |
| **家族以外に公開する場合** | プライバシーポリシー・利用規約・問い合わせ先の整備が必須になる | 特に子供の情報を扱うため、公開のハードルは高く見積もること |

### 1.3 アカウント削除

MVP ではセルフサービスの削除 UI を持たない（FR-A-6 を次フェーズ送り）。
依頼があった場合は運営者が Supabase ダッシュボード / CLI から手動で削除する
（`auth.users` の削除で profiles → family_members が cascade。家族データは families の削除で一括消去）。

## 2. 運用面の懸念と対応

### 2.1 無料枠の制約（最重要）

| 制約 | 影響 | 対応 |
|------|------|------|
| **Supabase 無料枠は 7 日間 API リクエストがないとプロジェクトが一時停止する** | 家族が使わない期間が続くと、次に開いたとき動かない | 週1回以上の利用が前提（成功指標と同じ）。停止したらダッシュボードから手動で Restore。運用が乗らないようなら Cron 等の keep-alive か Pro 化を検討 |
| DB 500MB / Storage 1GB / 帯域 5GB/月 | 写真が主な消費源 | クライアント圧縮（目安 300KB/枚）済み。靴 100 足でも約 30MB で問題なし |
| 自動バックアップは日次・保持 7 日（無料枠） | 誤削除に気づくのが遅れると復旧不能 | データ量が小さいので、必要になったら `supabase db dump` の手動取得で補完 |
| Auth のメール送信は実質テスト用 | パスワード認証を一般開放できない | 本番は Google OAuth のみ（設計通り） |
| Vercel Hobby は商用利用不可 | ― | 非商用の家族利用なので問題なし |

### 2.2 Google OAuth の運用

| 論点 | 状態 | 注意 |
|------|------|------|
| 同意画面の表示名 | `<project-ref>.supabase.co` が表示される | 解消には独自ドメイン + Supabase Custom Domain（有料）が必要。家族利用では許容 |
| 公開ステータス | テストモードの場合、**テストユーザーに登録したアカウントしかログインできない** | 家族のアカウントをテストユーザーに登録しておくこと |
| 検証なしアプリの制限 | テストモードでは refresh token の期限が短い場合がある | サインインし直せば済む。問題になるなら本番公開（検証申請）を検討 |

### 2.3 環境・シークレット管理

| 項目 | 方針 |
|------|------|
| 全環境が単一 Supabase プロジェクトを共有 | 開発ミスが本番データに直撃し得る。**破壊的な動作確認は専用のテスト Family を作って行う**こと |
| anon（publishable）キー | クライアント露出前提の設計。RLS が防御の本体なので漏洩自体は問題にならない |
| service_role キー | `.env.test`（gitignore 済み）のみ。アプリ・リポジトリには絶対に含めない |
| 認証設定の変更 | ダッシュボード手変更ではなく `supabase/config.toml` + `config push`（構成のコード管理を維持） |

### 2.4 障害時の切り分け

依存サービスは 2 つだけなので、切り分けは単純：

1. サイトが開かない → Vercel（[status.vercel.com](https://www.vercel-status.com/)）
2. 開くがログイン・データ取得が失敗 → Supabase（[status.supabase.com](https://status.supabase.com/)）。
   無料枠の**一時停止**をまず疑う（§2.1）
3. どちらも正常 → 直近のデプロイをロールバック（Vercel ダッシュボード or `vercel rollback`）

## 3. 見直しトリガー

以下のいずれかが起きたら本書を再検討する：

- [ ] 家族以外のユーザーを招待したくなった（→ 規約・ポリシー・Google 検証・Supabase Pro）
- [ ] Supabase の一時停止が 2 回以上発生した（→ keep-alive か有料化）
- [ ] 写真以外の子供の個人情報（生年月日等）を追加したくなった（→ 保存の必要性から再検討）
