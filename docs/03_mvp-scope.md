# 03. MVP スコープ整理

## 1. MVP の定義（このプロジェクトにおける）

> **妻が、店頭で、説明なしに、在庫を確認できる。**

これが達成できていれば MVP は成功。達成できていなければ、他が全部できていても失敗。

MVP の完成条件は「機能が揃うこと」ではなく **「実際に日常運用に乗ること」** とする。

## 2. スコープ In / Out

### 2.1 In（MVP に含む）

| # | 項目 | 対応要件 | 根拠 |
|---|------|----------|------|
| 1 | Google サインイン / サインアウト | FR-A-1〜3, 5 | 夫婦2端末で使うため |
| 2 | プロフィール自動作成 | FR-A-4 | 認証と業務データの接続に必須 |
| 3 | Family 自動作成 + 招待コード参加 | FR-F-1〜3 | データ共有の前提 |
| 4 | 子供の登録・切り替え | FR-C-1〜3 | 子供2人が前提 |
| 5 | **サイズ棚一覧（サイズ×カテゴリ）** | FR-L-1〜6 | ★中核価値 |
| 6 | 靴の登録（必須4 + 任意4） | FR-S-1〜5 | 中核価値の前提 |
| 7 | 写真アップロード（1枚・圧縮） | FR-S-5〜6 | 保管場所特定に実効性が高い |
| 8 | 靴の編集・削除 | FR-S-7〜8 | 記録の陳腐化を防ぐ |
| 9 | **1タップ状態変更** | FR-S-9 | 運用が続くかを左右する |
| 10 | PWA インストール | FR-X-1 | 起動速度＝参照速度 |
| 11 | **RLS によるデータ分離 + 自動テスト** | NFR-S-1〜6 | 公開する以上の必須条件 |

### 2.2 Out（MVP に含まない）

**次フェーズ候補（Should）**
- アカウント削除 UI（FR-A-6）— MVP では手動対応
- 子供の編集・削除（FR-C-4）
- 保管場所のサジェスト（FR-S-4 の一部）
- 直前入力の引き継ぎ（FR-S-10）
- オフライン閲覧キャッシュ（FR-X-2）
- 一覧への保管場所要約表示（FR-L-7）

**当面やらない（Could / Won't）**
- 検索・フィルタ・並べ替え（FR-L-8, 9）
- Family 名変更・メンバー管理 UI（FR-F-4, 5）
- 写真の複数枚 UI（FR-S-11）
- 通知 / 購入履歴 / EC 連携 / バーコード / AI / 成長予測 / 衣類管理（ブリーフ記載の除外項目すべて）
- アクセス解析、多言語対応、CSV 入出力

## 3. 実装フェーズ

各フェーズの終わりに動作するものが存在することを条件とする（大きな一括統合を避ける）。

### M0: 基盤（動くログイン）

| タスク | 完了条件 |
|--------|----------|
| Next.js プロジェクト作成 / Tailwind / TypeScript | `npm run dev` で起動する |
| Supabase プロジェクト作成、ローカル CLI 環境構築 | `supabase start` でローカル DB が立つ |
| Google OAuth 設定 | 実機ブラウザでサインインできる |
| 認証セッションの SSR 連携（@supabase/ssr） | リロードしてもセッションが維持される |
| 未認証リダイレクト | 保護ページに未認証で入れない |

**M0 の Exit 条件**: 自分の Google アカウントでサインインし、空のホーム画面が表示される。

### M1: データ基盤（正しさの担保）★最重要

| タスク | 完了条件 |
|--------|----------|
| 全テーブルのマイグレーション作成 | `supabase db reset` が通る |
| RLS ポリシー実装 | すべてのテーブルで `rls_enabled = true` |
| `is_family_member()` SECURITY DEFINER 関数 | 再帰エラーが起きない |
| プロフィール / Family 自動作成トリガー | 新規サインインで Family が1つできる |
| **RLS 統合テスト** | 他 Family のデータが 0 件 / 書き込み拒否になることを自動検証 |
| Storage バケットとポリシー | 他 Family の画像パスに署名 URL を発行できない |

**M1 の Exit 条件**: テストユーザー2名（別 Family）で、互いのデータが一切見えないことをテストが証明する。
**この Exit 条件を満たすまで UI 実装に進まない。** 後から RLS を足すのは事故のもと。

### M2: 中核機能（価値の実現）

| タスク | 完了条件 |
|--------|----------|
| 子供の登録・切り替え UI | 2人分登録して切り替わる |
| **サイズ棚一覧** | ブリーフの表示イメージどおりに描画される |
| 靴の登録フォーム（必須項目のみ） | 保存して一覧に反映される |
| 靴の詳細 / 編集 / 削除 | 一通り操作できる |
| 1タップ状態変更 | 一覧から状態が変わる |

**M2 の Exit 条件**: 自分の子供2人分の実データを全件投入し終える。
（テストデータではなく実データを入れることが検収を兼ねる）

### M3: 実用化（運用に乗せる）

| タスク | 完了条件 |
|--------|----------|
| 写真アップロード（圧縮 + 署名 URL 表示） | 撮影〜表示が実機で動く |
| 保管場所・メモ入力 | 詳細に表示される |
| 招待コード発行 / 参加 | 妻の端末で同じデータが見える |
| PWA（manifest / Service Worker / アイコン） | ホーム画面から起動できる |
| Vercel 本番デプロイ + 本番 Supabase | 本番 URL で動作する |
| エラーハンドリング / ローディング / 空状態 | 主要導線で破綻しない |

**M3 の Exit 条件 = MVP 完成条件**: §5 を参照。

### M4（MVP 後）: 定着の観察と改善

新機能を足さず、2〜4週間運用する。実際に使われなかった機能を削り、
使いにくかった箇所だけを直す。ここで初めて §2.2 の「次フェーズ候補」を検討する。

## 4. スコープ死守ルール

個人開発の最大の失敗要因は機能追加による未完成である。以下を運用ルールとする。

1. **MVP 中の新機能追加は原則却下**。思いついたら `docs/backlog.md` に書いて閉じる。
2. 既存要件の変更は、代わりに同等量の要件を落とすことを条件に許可する（ゼロサム）。
3. 「あとで困りそうだから今やる」は却下する。ただし **データモデルの変更を伴うもの** は例外として検討する（後からの移行が高コストなため）。
4. 判断に迷ったら [02](02_competitive-analysis.md) §4 の判断基準に照らす。
5. **NFR-S（セキュリティ）だけはスコープ削減の対象外**。

## 5. MVP 完成の判定基準（リリースチェックリスト）

### 機能

- [ ] 夫・妻それぞれの Google アカウントでサインインできる
- [ ] 2人が同じ Family に所属し、同じ靴データを見られる
- [ ] 子供2人を切り替えられ、選択が保持される
- [ ] サイズ棚一覧が、サイズ昇順・カテゴリ別・状態つきで表示される
- [ ] サイズアウトがデフォルト非表示で、トグルで表示できる
- [ ] 必須4項目のみで靴を登録できる
- [ ] 写真を撮影して登録・表示できる
- [ ] 保管場所と保管場所メモを登録・表示できる
- [ ] 編集・削除ができる
- [ ] 一覧から1タップで状態を変更できる
- [ ] PWA としてホーム画面から起動できる

### セキュリティ（1つでも未達ならリリース不可）

- [ ] 全テーブルで RLS が有効
- [ ] 別 Family のユーザーで SELECT / INSERT / UPDATE / DELETE が拒否されることをテストで確認済み
- [ ] Storage バケットが非公開で、別 Family の画像にアクセスできないことを確認済み
- [ ] クライアントバンドルに Service Role Key が含まれないことを確認済み
- [ ] RLS テストが CI で自動実行される

### 実運用

- [ ] 実データ（子供2人分の全靴）が投入済み
- [ ] 妻の端末にインストール済みで、説明なしに在庫確認ができた
- [ ] DB バックアップ方針が [09](09_legal-operational-concerns.md) に沿って設定済み
- [ ] Supabase 無料プランの一時停止対策が済んでいる

## 6. 撤退・見直し基準

| 条件 | アクション |
|------|-----------|
| M1 の RLS テストが通らない状態が続く | UI を進めず、データモデルを簡素化して再設計する |
| 妻が2週間使わない | 機能追加ではなく、UI/導線を疑って観察・修正する |
| MVP が3ヶ月で完成しない | スコープを M2 まで（写真・招待なし・自分専用）に切り下げて完成させる |
| 重複購入が引き続き発生する | 「一覧の見え方」を根本から作り直す（機能追加ではない） |

## 7. 意図的に MVP へ含めた「重い」項目とその理由

MVP を軽くする観点では削りたいが、後から入れるコストが高いため先行実装する。

| 項目 | 通常なら後回し | 先行する理由 |
|------|----------------|--------------|
| RLS + データ分離 | 家庭内利用だけなら不要 | 後付けは全クエリの見直しが必要。公開の可能性がある以上、初期から必須 |
| Family / FamilyMember | 単一ユーザーなら不要 | 後から多対多を入れるのは全テーブルの移行になる |
| 非公開 Storage + 署名 URL | public バケットが楽 | 一度公開 URL で運用すると、移行時に既存 URL が全部壊れる |
| `shoes.family_id` の非正規化 | 正規化のままでよい | RLS のポリシー簡潔性と性能に直結する（[05](05_database-design.md) §3.6） |
