# 02. 競合分析

## 0. 本書の位置づけと注意

本プロダクトは家庭内利用を主目的とする MVP であり、市場を奪いに行く事業ではない。
したがって本書の目的は **市場シェアの分析ではなく、「なぜ既存手段で解決できていないのか」を言語化し、作るべきものの輪郭を絞ること** にある。

> **注意**: 以下の個別プロダクトに関する記述は、一般に知られた特徴に基づく概観であり、
> 各サービスの最新の機能・料金を逐一検証したものではない。
> 意思決定に効く箇所（特に §5 の代替コスト）は、実装着手前に実機で確認することを推奨する。
> 分析の主対象は個別製品ではなく **「解決手段のカテゴリ」** としている。

## 1. 競合の定義

「子供靴ストック管理」という直接競合はほぼ存在しない。真の競合は **現在ユーザーが使っている代替手段** である。

```text
競合の階層

[直接競合]      子供の靴／子供服の在庫管理に特化したアプリ
                   ↑ 存在するが数が少なく、継続率も低いと見られる

[間接競合]      汎用の持ち物・在庫管理アプリ（Sortly 等）
                汎用データベースアプリ（Airtable / Notion / Memento 等）

[代替手段] ★    スプレッドシート、メモアプリ、写真アプリ、
                LINE の自分宛メッセージ、そして「記憶」
                   ↑ 実際の競合はここ。特に「記憶」が最大の競合
```

**最大の競合は「何もしない（記憶に頼る）」である。**
この前提を外すと、「高機能だが誰も入力しないアプリ」を作ることになる。

## 2. カテゴリ別分析

### 2.1 記憶（現状 / シェア圧倒的1位）

| 観点 | 評価 |
|------|------|
| 導入コスト | 0 |
| 入力コスト | 0 |
| 参照速度 | 一見速いが **不正確** |
| 共有 | 不可（夫婦間で口頭確認が必要） |
| 破綻条件 | ストック数が増える / 期間が空く / サイズとカテゴリの掛け算が増える |

**示唆**: 記憶に勝つには「入力コストが記憶とほぼ同等」でなければならない。
入力に3分かかるアプリは、記憶に負ける。→ FR-S-1〜S-3（必須4項目のみ・ステッパー入力）の根拠。

### 2.2 スプレッドシート（Google スプレッドシート等）

| 観点 | 評価 |
|------|------|
| 強み | 無料 / 柔軟 / 夫婦での共有が容易 / 既に使い慣れている |
| 弱み | **スマホでの閲覧体験が悪い**（横スクロール、セル選択、ズーム） |
| 弱み | 写真の添付が実質困難（セル内画像は扱いにくい） |
| 弱み | 入力時にキーボードとセル移動が必要で、片手操作に向かない |
| 弱み | 「サイズ×カテゴリの在庫マトリクス」を見やすく保つ運用が属人的 |

**示唆**: 機能で負けているのではなく **モバイル UI で負けている**。
本プロダクトの主な価値は「データモデル」ではなく「スマホ最適化された参照ビュー」にある。
→ FR-L-1〜L-5（サイズ棚ビュー）が唯一の差別化点であり、ここに実装工数を集中する。

### 2.3 メモアプリ / LINE 自分宛

| 観点 | 評価 |
|------|------|
| 強み | 入力が最速。写真も貼れる |
| 弱み | 構造化されないため、**検索性と一覧性がゼロ** |
| 弱み | 情報が時系列に流れ、最新の在庫状況が分からない |

**示唆**: 「入力の速さ」ではメモに勝てない。勝てるのは「一覧の作れなさ」の部分。
→ 入力速度はメモに近づけつつ（Must）、価値の主張は一覧に置く。

### 2.4 汎用在庫・持ち物管理アプリ（Sortly 等）

一般に、写真つきアイテム管理・保管場所（ロケーション）階層・QR ラベル・数量管理などを備える。

| 観点 | 評価 |
|------|------|
| 強み | 保管場所管理・写真管理は本プロダクトより高機能 |
| 弱み | **子供靴のドメイン概念（サイズ / 用途カテゴリ / サイズアウト）を持たない**ため、自前でカスタムフィールドを設計する必要がある |
| 弱み | 「サイズ順に並べ、用途別の欠品を見る」ビューを作れない（作れても手間がかかる） |
| 弱み | 多くが有料プラン前提（アイテム数上限あり） |
| 弱み | UI が英語または業務寄りで、配偶者が使い続けるハードルが高い |

**示唆**: 汎用ツールは「入れ物」は提供するが「見え方」は提供しない。
本プロダクトは逆に、**見え方だけを提供する専用ツール**として成立する。

### 2.5 汎用データベースアプリ（Airtable / Notion / Memento Database 等）

| 観点 | 評価 |
|------|------|
| 強み | 何でも作れる。共有も可能 |
| 弱み | **設計・構築コストが高く、家族の非エンジニアが使い続けにくい** |
| 弱み | モバイルアプリの起動が重い、オフライン挙動が不安定なものがある |
| 弱み | 無料枠の制限（レコード数・共有人数）に注意が必要 |

**示唆**: 開発者本人は使えても、**妻が使わなければ意味がない**。
「妻が説明なしで使えること」という要件（01 §3.1）は、このカテゴリを排除する決定的な理由になる。

### 2.6 子供服・おさがり管理系アプリ（直接競合）

子供服の管理、サイズ管理、おさがり共有を掲げるアプリはいくつか存在する。一般的な傾向として：

| 観点 | 評価 |
|------|------|
| 強み | ドメインが近く、サイズ概念を持つ |
| 弱み | 衣類が主対象で、**靴の「用途カテゴリ」概念がない**（家/園庭/上履きの区別が付けられない） |
| 弱み | 個人開発が多く、更新停止・サービス終了リスクがある |
| 弱み | 機能過多（コーディネート、フリマ連携、成長記録）で起動〜参照が遅くなりがち |

**示唆**: 完全に競合するものは見つけにくい。ただし「サービス終了リスク」は
自作の妥当性を補強する（自分のデータを自分で持てる）。

## 3. 比較マトリクス

◎=優れる ○=可 △=不十分 ×=不可

| 評価軸（重み） | 記憶 | スプレッドシート | メモ/LINE | 汎用在庫アプリ | Notion系 | 子供服アプリ | **本プロダクト** |
|---|---|---|---|---|---|---|---|
| 購入時の参照速度 **(★最重要)** | △ | △ | × | ○ | △ | ○ | **◎** |
| サイズ×カテゴリの一覧性 **(★最重要)** | × | ○ | × | △ | ○ | △ | **◎** |
| 入力の手軽さ (★) | ◎ | △ | ◎ | ○ | △ | ○ | **○** |
| 保管場所の記録 (★) | × | ○ | ○ | ◎ | ○ | △ | **◎** |
| 写真 | × | × | ◎ | ◎ | ○ | ◎ | **○** |
| 夫婦での共有 | × | ◎ | × | △ | ○ | △ | **◎** |
| 学習コストの低さ | ◎ | ○ | ◎ | △ | × | ○ | **◎** |
| 継続性（サービス終了しない） | ◎ | ◎ | ◎ | ○ | ○ | △ | **◎** |
| コスト | ◎ | ◎ | ◎ | △ | △ | ○ | **◎** |

**読み取り**: 本プロダクトは「写真」「入力の手軽さ」で既存手段に勝てない。
勝てるのは **参照速度・一覧性・共有・学習コストの組み合わせ**。
したがって写真機能に凝るのは投資対効果が悪く、一覧 UI に工数を寄せるべき。

## 4. 差別化の中核（Value Proposition）

> **「サイズ×用途カテゴリの在庫マトリクスを、スマホで3タップ・5秒で読めること」**

これ以外はすべて補助機能である。以下の判断基準を実装中の意思決定に用いる。

| 判断基準 | 適用例 |
|----------|--------|
| 一覧の視認性を上げる変更は優先する | サイズ棚のグルーピング、状態バッジの配色 |
| 一覧の表示速度を下げる変更は却下する | 一覧での画像の即時ロード（→ サムネイル遅延 or 非表示） |
| 入力項目を増やす提案は原則却下する | 購入日、価格、サイズ表記の複数規格対応 |
| 「あると便利」は Could 以下に落とす | 検索、フィルタ、並べ替え |

## 5. 「作らない」場合の比較（Build vs Buy）

自作は最もコストが高い選択肢であるため、明示的に正当化しておく。

| 選択肢 | 初期コスト | 運用コスト | 要件充足 | 判定 |
|--------|-----------|-----------|----------|------|
| スプレッドシート運用 | 1時間 | 低 | 参照体験 △（最重要要件を満たさない） | 却下 |
| 汎用在庫アプリの課金利用 | 3時間 | 月額 + 学習 | 一覧性 △、妻の学習コスト大 | 却下 |
| Notion テンプレート構築 | 5時間 | 中 | 妻が使い続けない可能性が高い | 却下 |
| **自作（本プロジェクト）** | 数十時間 | 低（無料枠内） | 全要件を満たせる。学習機会にもなる | **採用** |

**自作の追加的な正当性**
- 開発者本人にとって Next.js + Supabase の実践機会になる（学習価値がコストの一部を相殺する）。
- データを自分で保持でき、サービス終了リスクがない。
- ドメインが小さく、MVP を現実的な工数で完成できる。

**自作のリスク**: 開発者が飽きた時点でメンテが止まる。
→ 対策として **機能を増やさない**。スコープ拡大こそが最大の失敗要因である（[03](03_mvp-scope.md)）。

## 6. 本分析から設計へのインプット（要約）

| 分析からの結論 | 反映先 |
|----------------|--------|
| 最大の競合は「記憶」。入力コストを極限まで下げる | 01 FR-S-1〜S-3, S-10 |
| 勝ち筋はモバイル最適化された一覧ビューのみ | 01 FR-L-1〜L-5 / 03 の最優先タスク |
| 写真は必須だが差別化要素ではない。凝らない | 01 FR-S-5〜S-6（1枚・圧縮のみ） |
| 妻が説明なしで使えることが撤退ラインの判定基準 | 01 §2.2 成功指標 |
| 機能追加はプロダクトを殺す方向に働く | 03 §4 スコープ死守ルール |
