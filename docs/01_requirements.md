# 01. 要件定義

> 本書は `PROJECT_BRIEF.md` を出発点に、実装可能な粒度まで要件を具体化したもの。
> ブリーフと矛盾する場合はブリーフを正とし、本書を修正する。

## 1. 背景と課題

子供は成長が早く、セール等のタイミングで「将来使うサイズ」の靴を先買いしてストックする家庭がある。
しかし在庫が記憶と物理的な保管場所に依存しているため、以下が発生している。

| ID | 課題 | 発生タイミング | 影響 |
|----|------|----------------|------|
| P-1 | 既に持っているサイズを重複購入する | 店頭・EC での購入時 | 金銭的損失 |
| P-2 | 必要なサイズを持っているか即座に確認できない | 購入検討時 | 判断の遅延・買い逃し |
| P-3 | ストックした靴の保管場所が分からない | サイズアップ時 | 探索コスト、事実上の紛失 |
| P-4 | 用途（家/園庭/上履き）ごとの在庫が把握しづらい | 進級・季節の変わり目 | 直前の慌てた買い足し |

課題の中心は **記録の欠如ではなく「購入時に3秒で参照できないこと」** にある。
したがって本プロダクトの成否は、登録機能の豊富さではなく **参照体験の速さ** で決まる。

## 2. プロダクトゴール

### 2.1 プロダクトゴール（定性）

- 店頭で靴を手に取った状態から **3タップ以内・5秒以内** に「そのサイズ×カテゴリの在庫有無」を確認できる。
- ストックの保管場所を、写真とメモつきで確実に思い出せる。
- 夫婦のどちらが登録しても、もう一方が同じ情報を見られる。

### 2.2 成功指標（MVP）

MVP は家庭内利用が主目的のため、定量指標は最小限とする。

| 指標 | 目標 | 計測方法 |
|------|------|----------|
| 妻が自発的に週1回以上アプリを開く | 4週連続 | 口頭ヒアリング（分析ツールは MVP 対象外） |
| 重複購入の発生 | 0件 / 3ヶ月 | 同上 |
| 靴1件の登録所要時間 | 60秒以内 | 手動計測 |
| 在庫確認の所要時間 | 5秒以内（アプリ起動後） | 手動計測 |

> 注: MVP ではアクセス解析ツールを導入しない（[09_legal-operational-concerns.md](09_legal-operational-concerns.md) のプライバシーポリシー負担を避けるため）。

## 3. 対象ユーザー

### 3.1 プライマリペルソナ：妻（主利用者）

- 30代、子供2人（未就学児）の保育園送迎を担当。
- スマートフォン中心。PC はほぼ使わない。
- 買い物中に片手でアプリを操作する。
- **アプリの学習に時間をかけたくない。** 説明なしで使えることが必須。

### 3.2 セカンダリペルソナ：夫（開発者本人）

- 靴の登録・写真撮影・保管場所の記録を主に担当。
- 開発者でもあるため、運用・障害対応も担う。

### 3.3 将来ユーザー

一般公開を想定するが、MVP では獲得施策を行わない。
ただし **他人が使っても他家庭のデータが見えない構成** は MVP 時点で必須（§6 セキュリティ要件）。

## 4. 用語定義

| 用語 | 定義 |
|------|------|
| Family | データ共有の単位。1家庭 = 1 Family。 |
| User | Supabase Auth の認証ユーザー。Google アカウントと 1:1。 |
| FamilyMember | User と Family の所属関係。1 User が複数 Family に所属可能な設計とする（MVP では 1:1 運用）。 |
| Child | Family に属する子供。MVP では長男・次男の2名。 |
| Shoe | Child に属する靴1足。同一サイズ・同一カテゴリでも複数レコード登録可能。 |
| カテゴリ | 靴の用途区分。`home` / `yard` / `indoor` の固定3値。 |
| 状態 | 靴のライフサイクル。`in_use` / `stock` / `outgrown` の固定3値。 |
| サイズ | 靴のサイズ（cm）。0.5cm 刻み。 |
| サイズ棚 | 一覧画面で同一サイズの靴をまとめて表示する行グループ。 |

## 5. 機能要件

優先度は MoSCoW（Must / Should / Could / Won't）。MVP は **Must のみ** を対象とする。
詳細な段階分けは [03_mvp-scope.md](03_mvp-scope.md) を参照。

### 5.1 認証・アカウント（FR-A）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-A-1 | Google アカウントでサインインできる | Must |
| FR-A-2 | サインイン状態が端末に永続化され、次回起動時に再認証不要 | Must |
| FR-A-3 | サインアウトできる | Must |
| FR-A-4 | 初回サインイン時、プロフィール（表示名・メール）が自動作成される | Must |
| FR-A-5 | 未認証ユーザーはサインイン画面以外にアクセスできない | Must |
| FR-A-6 | アカウント削除（全データ削除）ができる | Should |
| FR-A-7 | Google 以外の認証方式（メールリンク等） | Won't |

### 5.2 Family（FR-F）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-F-1 | 初回サインイン時、所属 Family がなければ Family を自動作成し、作成者を所属させる | Must |
| FR-F-2 | 招待コードを発行し、配偶者が同じ Family に参加できる | Must |
| FR-F-3 | 招待コードには有効期限がある | Must |
| FR-F-4 | Family 名を変更できる | Could |
| FR-F-5 | メンバーを一覧・削除できる | Could |
| FR-F-6 | 1ユーザーが複数 Family を切り替える UI | Won't（データモデルのみ対応） |

> **設計判断**: 招待は「メール招待」ではなく「招待コード共有」とする。
> 夫婦間は LINE 等で手軽に共有でき、メール送信基盤（およびその到達性の運用）を持たずに済むため。

### 5.3 Child（FR-C）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-C-1 | Family に子供を登録できる（名前のみ必須） | Must |
| FR-C-2 | 一覧画面上部で子供をタップ1回で切り替えられる | Must |
| FR-C-3 | 選択中の子供が次回起動時も保持される | Must |
| FR-C-4 | 子供を編集・削除できる | Should |
| FR-C-5 | 子供の表示順を並べ替えられる | Could |
| FR-C-6 | 生年月日・足のサイズ記録・成長予測 | Won't |

### 5.4 靴一覧（FR-L） ★プロダクトの中核

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-L-1 | 選択中の子供の靴を **サイズ昇順** で一覧表示する | Must |
| FR-L-2 | 同一サイズをグループ化し、カテゴリ3種の在庫有無を1画面で示す | Must |
| FR-L-3 | 各セルは状態（使用中/ストック/サイズアウト/なし）を色とラベルで区別する | Must |
| FR-L-4 | 「なし」のカテゴリも表示する（欠品が分かることが重要） | Must |
| FR-L-5 | サイズアウトはデフォルトで非表示（トグルで表示） | Must |
| FR-L-6 | 靴をタップすると詳細を表示する | Must |
| FR-L-7 | 一覧に保管場所を要約表示する | Should |
| FR-L-8 | サイズ・カテゴリ・状態で絞り込める | Could |
| FR-L-9 | ブランド名等のフリーワード検索 | Won't |

**FR-L-2 の表示イメージ（ブリーフ準拠）**

```text
18.0cm
  家（登園）  ストック   押入れ上段
  園庭        ストック   押入れ上段
  上履き      なし
```

### 5.5 靴の登録・編集（FR-S）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-S-1 | 必須項目（子供・サイズ・カテゴリ・状態）で登録できる | Must |
| FR-S-2 | 任意項目（ブランド・写真・保管場所・保管場所メモ）を登録できる | Must |
| FR-S-3 | サイズは 0.5cm 刻みのステッパー/選択式で入力する（自由数値入力にしない） | Must |
| FR-S-4 | 保管場所は自由入力＋過去入力値のサジェスト | Must（サジェストは Should） |
| FR-S-5 | 写真をカメラ撮影またはライブラリから1枚登録できる | Must |
| FR-S-6 | 写真はアップロード前にクライアントでリサイズ・圧縮する | Must |
| FR-S-7 | 登録済みの靴を編集できる | Must |
| FR-S-8 | 靴を削除できる（確認ダイアログあり） | Must |
| FR-S-9 | 一覧/詳細から **1タップで状態を変更** できる（ストック→使用中、使用中→サイズアウト） | Must |
| FR-S-10 | 直前に登録した内容（子供・カテゴリ・保管場所）をフォーム初期値に引き継ぐ | Should |
| FR-S-11 | 写真を複数枚登録できる | Could（DB は複数枚対応で設計） |
| FR-S-12 | 購入日・購入価格・購入店の記録 | Won't |

### 5.6 非機能に近い機能要件（FR-X）

| ID | 要件 | 優先度 |
|----|------|--------|
| FR-X-1 | PWA としてホーム画面に追加でき、スタンドアロン表示で起動する | Must |
| FR-X-2 | オフライン時、直前に取得した一覧をキャッシュから表示する | Should |
| FR-X-3 | オフラインでの登録・編集（同期キュー） | Won't |
| FR-X-4 | プッシュ通知 | Won't |

## 6. 非機能要件

### 6.1 セキュリティ / データ分離（最重要）

| ID | 要件 | 検証方法 |
|----|------|----------|
| NFR-S-1 | 他 Family のデータは、API を直接叩いても取得・変更できない | RLS 統合テスト（[05](05_database-design.md) §7） |
| NFR-S-2 | すべてのアプリケーションテーブルで RLS を有効化する | マイグレーション CI チェック |
| NFR-S-3 | アクセス制御をクライアント UI に依存しない | 同上 |
| NFR-S-4 | Storage の画像も Family 単位でアクセス制御する（public バケット禁止） | Storage ポリシーテスト |
| NFR-S-5 | Service Role Key をクライアントバンドルに含めない | ビルド成果物の文字列検査 + CI |
| NFR-S-6 | 認証・認可のテストを自動化し、CI で実行する | CI 必須ジョブ |

> **NFR-S-1 は本プロダクト唯一のリリースブロッカー**。他機能が未完成でもリリースし得るが、
> データ分離が検証できていない状態では公開しない。

### 6.2 パフォーマンス

| ID | 要件 | 目標 |
|----|------|------|
| NFR-P-1 | 一覧画面の LCP（モバイル 4G 相当） | 2.5秒以内 |
| NFR-P-2 | 子供の切り替え | 200ms 以内（クライアント側で完結、再フェッチしない） |
| NFR-P-3 | 一覧の初期取得件数 | 1家庭あたり数百件を想定。ページングは不要 |
| NFR-P-4 | 写真アップロード | 1枚あたり 5秒以内（圧縮後 300KB 目安） |

### 6.3 可用性・運用

| ID | 要件 |
|----|------|
| NFR-O-1 | 個人開発のため SLA は定義しない。ダウンタイムは許容する |
| NFR-O-2 | データ損失は許容しない。DB バックアップ方針を定める（[09](09_legal-operational-concerns.md) §6） |
| NFR-O-3 | Supabase 無料プランの非アクティブ一時停止リスクに対処する（[09](09_legal-operational-concerns.md) §5） |

### 6.4 対応環境

| 項目 | 対象 |
|------|------|
| 主対象 | iOS Safari 最新2バージョン / Android Chrome 最新2バージョン |
| 副対象 | デスクトップ Chrome（開発・確認用） |
| 画面幅 | 360px 〜 430px を最適化。768px 以上は中央寄せカラム |
| 非対応 | IE、iOS Safari の2世代以上前 |

### 6.5 アクセシビリティ

| ID | 要件 |
|----|------|
| NFR-A-1 | 状態の区別を **色のみに依存しない**（ラベル文言を併記） |
| NFR-A-2 | タップターゲットは 44×44px 以上 |
| NFR-A-3 | 主要導線でコントラスト比 4.5:1 以上 |

### 6.6 国際化

日本語のみ。i18n 基盤は導入しない（サイズ表記も cm 固定）。

## 7. 主要ユースケースと受け入れ基準

### UC-1: 買う前に在庫を確認する（最重要）

```text
前提: サインイン済み、ホーム画面にPWAアイコンがある
1. ホーム画面のアイコンをタップ
2. 一覧画面が表示され、前回選択していた子供が選択済み
3. （必要なら）子供タブをタップして切り替え
4. 目的のサイズ行までスクロール
5. カテゴリ別の在庫有無を確認
```

**受け入れ基準**
- 起動から在庫確認まで、追加のログイン操作が発生しない。
- 起動から一覧の描画完了まで 2.5 秒以内（NFR-P-1）。
- 「なし」のカテゴリが空欄ではなく明示的に「なし」と表示される。

### UC-2: ストックした靴を探す

```text
1. 一覧で対象の靴をタップ
2. 詳細に保管場所・保管場所メモ・写真が表示される
```

**受け入れ基準**
- 保管場所が未登録の場合、「未設定」と明示され、その場で追加できる導線がある。
- 写真は詳細画面でタップ拡大できる。

### UC-3: 新しい靴をストックする

```text
1. 一覧右下の FAB をタップ
2. 子供・サイズ・カテゴリ・状態を入力（状態の初期値は「ストック」）
3. 保管場所を入力（直前の入力値がサジェストされる）
4. 写真を撮影
5. 保存 → 一覧に戻り、追加された靴がハイライトされる
```

**受け入れ基準**
- 必須4項目のみで保存できる（写真なしでも保存可能）。
- 写真アップロード中も他の入力が可能で、保存はアップロード完了を待つ。
- 保存失敗時、入力内容が失われない。

### UC-4: サイズアウトした靴を片付ける

```text
1. 一覧で使用中の靴の状態バッジをタップ
2. 「サイズアウトにする」を選択
3. 一覧から消える（サイズアウト表示トグルで再表示可能）
```

**受け入れ基準**
- 確認ダイアログを挟まずに1タップで完了する（誤操作は Undo トーストで戻せる）。

### UC-5: 配偶者を家族に招待する

```text
1. 設定 → 家族 → 招待コードを発行
2. コードを LINE 等で共有
3. 配偶者がサインイン後、コードを入力して参加
4. 同じ靴データが表示される
```

**受け入れ基準**
- 有効期限切れ・使用済みコードは明確なエラーメッセージで拒否される。
- 参加後、配偶者が登録した靴を発行者側でも閲覧・編集できる。

## 8. 制約と前提

| 種別 | 内容 |
|------|------|
| 前提 | 利用者は Google アカウントを保有している |
| 前提 | 常時オンライン環境で利用する（オフラインは閲覧のみのベストエフォート） |
| 制約 | 開発者1名。運用工数を要する機能は採用しない |
| 制約 | ランニングコストは無料枠内を原則とする |
| 制約 | 靴以外のカテゴリ（衣類等）は MVP で扱わない |

## 9. スコープ外（MVP で実装しないもの）

ブリーフ記載のとおり、以下は実装しない。

衣類・おもちゃ等の靴以外の管理 / AI 機能 / サイズ自動推定 / 足のサイズ記録 / 成長予測 /
通知 / 購入履歴 / EC 連携 / バーコード・QR / SNS 機能 / 管理画面 / 複雑な権限管理 /
家族以外とのデータ共有

加えて、本設計で明示的に除外するもの：

- アクセス解析・行動ログ収集
- 多言語対応
- メール送信機能
- CSV エクスポート／インポート
- 監査ログ UI（DB 側の `created_at` / `updated_at` のみ保持）
